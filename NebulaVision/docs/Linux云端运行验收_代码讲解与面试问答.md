NebulaVision 学习记录　2026年11月3日

验收结论：Ubuntu24.04云端两个正式程序与验收入口构建成功，13项运行检查全部通过，包括真实模型、视频帧、异常短片、回放以及本次新增的录像恢复与连续序号回归。这是已测核心功能的结论，不是所有Linux硬件与部署场景均已完成。

本次在 GitHub 托管的 Ubuntu 24.04 中测试项目，用临时 MySQL、新生成的测试账号、公开样本和真实模型验证运行。没有启动用户的 VMware，也没有上传本机数据库、密码或真实摄像头画面。以前“Linux 尚未验收”的文档保留为历史记录，本篇给出新证据。

## 1 编译与运行验收有什么区别

编译把 C++ 源码变成 Linux 可执行文件；运行还需要 Qt 插件、数据库驱动、系统库、FFmpeg、Python 和模型。编译成功只能说明构建通过，不能说明登录、视频、数据库和模型都能工作。

云端没有实体显示器，所以使用 Xvfb 提供虚拟 X11 显示器，让真实 Qt Widgets 窗口运行。程序接收解码帧、调用模型、生成 MP4、查询事件，再实际播放，并非给界面截图画一个假视频框。

本次使用公开手掌图片生成循环视频，还用公开人物图片验证 YOLO。它们用于检查代码链路和运行依赖，不用于证明现场识别准确率。云端没有用户的 USB 摄像头，也无法直接访问远程 Seetong 摄像头。

## 3 修改文件和职责

.github/workflows/build.yml：把已有的 Ubuntu 编译任务扩展成构建与运行验收。安装 Linux 系统依赖、Qt6.11.2、Python3.12、MySQL、Redis 和 FFmpeg；检查匹配的 Qt MySQL 插件；编译正式程序与测试入口；最后执行验收并上传有限的证据文件。

CMakeLists.txt：新增 NEBULAVISION_ACCEPTANCE 选项，默认关闭。开启时多生成 linux_gui_acceptance，不替代正式的 class15 和 nebulavision_server。测试入口位于 tests 子目录，头文件搜索范围需要显式包括项目根目录。

tests/linux_acceptance.py：准备隔离测试库、生成临时账号、下载并验证模型，启动后台和 Qt 测试，检查接口、真实推理、视频与重启恢复。仅允许 Linux 且 NEBULAVISION_CI=1 时运行；发现已有同名业务库就拒绝，防止覆盖用户数据库。

tests/linux_acceptance_gui.cpp：运行原 MainWidget、MonitorWidget、LivePreview 和 ReviewWidget。先确认监控播放器实际收到帧，再通过真实手势模型触发异常短片，最后双击关联事件，检查回放帧、拖动与倍速。没有把“窗口没崩溃”当成“视频已显示”。

本次新增录像恢复回归复用 tests/clip_recovery_check.cpp，以编译宏关闭其独立main，再由已有Qt验收入口调用，避免创建第二个QApplication；具体业务修复见同期《录像重试与编号修复》。

本次文档记录代码和验收方法；项目首页及文档目录随后指向本篇。正常 Windows 启动器和本机数据库配置没有因本次云端测试被替换。

## 4 从提交到云端结果

调用顺序：Git 提交 → GitHub Actions 的 Ubuntu 任务 → 安装依赖 → CMake 构建 → linux_acceptance.py → 启动 C++ 后台和 Python 检测进程 → Xvfb 中运行 linux_gui_acceptance → 保存 JSON 报告和公开样本截图 → 停止本次进程。

YAML 是工作流配置格式。steps 表示顺序执行的步骤；run 后面是执行的命令；env 表示传给程序的环境变量。它不是 C++ 代码，也不是另一份数据库。

```text
cmake -S . -B build -DNEBULAVISION_ACCEPTANCE=ON
cmake --build build --parallel 2
python tests/linux_acceptance.py build
```

第一行根据当前源码生成构建规则，打开验收入口；第二行实际调用编译器，最多同时两个构建任务；第三行在已经准备好的隔离 Linux 环境执行验收。不能在普通电脑上只复制第三行，就认为依赖、账号和 MySQL 会自动齐全。

## 5 为什么测试库和账号单独生成

正式服务强制使用 nebulavision_dev。云端使用一台干净临时机器，先检查没有这个库，再执行0001至0005迁移，不导入用户本机数据。数据库服务账号和业务登录账号分别生成随机口令；业务密码按现有 PBKDF2 哈希格式写入 users 表。

测试配置放在本次 Linux runner 的临时目录，不提交 Git。上传证据只允许报告、日志和公开样本截图，配置文件、账号文件、模型和录像原文件不包含在证据包内。测试结束后，托管 runner 的临时环境由平台回收。

环境变量 NEBULAVISION_SERVER_CONFIG 指定本次服务配置，NEBULAVISION_RESOURCES_ROOT 指定模型和录像目录，NEBULAVISION_AGENT_PYTHON 指定本次 Python。路径由运行环境产生，避免把 Windows 的 E盘和 exe 文件名当作 Linux 路径。

现有 Windows 的 CMD、PowerShell 启动器和部分本机辅助测试仍有 Windows 路径。本次通过独立的可复现 Linux 验收入口验证，不表示它们已经变成 Linux 一键安装器。

## 6 怎样证明真正出画面和保存了录像

```cpp
connect(player, &FfmpegPlayer::frameDisplayed, &app, [&]() {
    ++frames;
});
```

这里连接原播放器实际显示帧的信号，收到一帧计数加一。[&] 让 Lambda 使用外部计数变量的引用，修改的是原计数。变量在整个测试函数运行期间有效；不能把这种引用捕获随意带进比变量活得更久的后台任务。

测试不是调用 play 就算成功，而是等待若干真实帧。实时模型结果触发事件后，还要等“异常录像已保存”，查到大于0的关联录像编号，再授权下载并让 FFmpeg 真正解码文件。

回放使用原 ReviewWidget 的播放器与控件，检查 QVideoSink 收到有效帧、媒体时长有效、可以跳转到中间，并把实际 playbackRate 调到2。测试时还确认回放页可见、监控页没有被自动切回。

Python 检测服务使用模型清单指定的 SHA256 校验权重，测试检查 synthetic 为 false、模型版本一致，并通过公开人物图得到人员检测结果。另从 C++ API 提交已有录像的检测任务，验证 Python gRPC 适配器这条进程链路。

## 7 停止与恢复怎样验证

测试创建一条仅用于验收的 writing 录像索引，停止后台后再启动，检查它是否变为 interrupted；旧登录会话也应失效。它验证程序启动恢复逻辑，而不是假装恢复出从未保存的视频。

所有启动进程都保存在本次测试的进程对象列表中，finally 中按反向顺序停止并等待退出。退出后检查这些进程确实已结束。这个清理范围只属于本次云端任务，不会按名字批量结束其他人的程序。

突然断电、磁盘满、多日持续录像、文件与数据库孤立记录对账仍需单独验收。正常重启通过不能被写成所有灾难恢复场景都通过。

## 8 本次排查记录

第一轮运行的正式程序已具备 Linux 构建基础，但新增验收程序编译时找不到 util/winmanager.h。原因是该文件从 tests 子目录引用项目根目录下的头文件，而新增 CMake 目标只加了 util 搜索路径。修复时增加 CMAKE_CURRENT_SOURCE_DIR，未通过复制一份头文件或删除测试来绕开问题。

本机到 github.com 的 Git HTTPS 连接一度重置，发布改用 GitHub 官方 Git Data API，核对文件对象、目录树和提交 SHA 一致后才更新远程分支。它没有更换源码或跳过验收。

第二轮三个 C++ 目标均已构建完成，但模型依赖安装失败。日志显示 Qt 安装动作内部又调用了 Python 设置动作，把 PATH 中的解释器变成3.15，尽管工作流较早已选3.12。修复为在 Qt 安装后再次固定 Python3.12，并在日志中打印版本；没有通过删除 ONNX Runtime 或把真实模型换成模拟数据来跳过问题。

第三轮11项功能检查全部通过，但人工查看实际截图时发现中文变成方块。原因是干净 Ubuntu 没有中文字体，功能返回成功也不能掩盖这个显示问题。工作流随后安装 fonts-noto-cjk，增加字体存在检查，再重新验证界面与功能。

日志中的“未找到硬件解码器”和缺少 PipeWire 库提示，没有使本次文件视频解码失败；本轮使用软件解码，不包含 PipeWire 摄像头或声音采集验收。

## 9 面试问题与继续追问

问题1：编译通过和 Linux 能运行一样吗？答：不一样，运行还需要系统库、Qt 平台与 SQL 插件、外部工具和配置。追问：你怎样证明运行？追答：在 Ubuntu 上启动真实服务与控件，检查接口、数据库结果和视频帧，报告列出实际证据和未测项。

问题2：没有显示器怎么测 Qt？答：Xvfb 提供虚拟 X11 显示器，Qt 仍运行真实窗口。追问：这能证明实体摄像头正常吗？追答：不能，云端使用文件样本，USB 权限、驱动和硬件需要现场验证。

问题3：为什么不用开发者的数据库做云端测试？答：会带来数据污染和秘密泄露风险，所以使用干净临时库和随机测试账号。追问：脚本误跑到已有库怎么办？追答：有 Linux CI 环境检查，且库存在就拒绝继续，不会先删库重建。

问题4：进度条动了就代表回放成功吗？答：还不够，要确认实际视频帧、时长、录像关联，以及跳转后的实际位置和速度。追问：只测按钮文字可以吗？追答：不行，文字可能更新而底层播放失败，本次检查的是播放器状态与有效帧。

问题5：模型测试如何避免拿演示返回冒充？答：校验模型哈希、synthetic=false 和模型版本，并走真实推理和 gRPC 适配链路。追问：公开样本通过能证明准确率吗？追答：不能，它证明链路可运行，准确率需要专门的数据集与评价指标。

问题6：有云端通过记录就能说 Linux 全部完成吗？答：只能说这台 Ubuntu、这套依赖和已测场景通过。追问：还缺什么？追答：实体摄像头、MediaMTX 网络链路、Agent全流程、不同发行版、长期压力以及 Linux 一键部署等仍需分别验证。
