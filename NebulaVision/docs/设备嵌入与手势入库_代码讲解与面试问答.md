## 3 双击设备之后发生什么

调用顺序：设备双击信号 → MonitorWidget::openDevice → 获得本机摄像头或授权视频地址 → 创建 LivePreview → embedLive → openCamera 或 openStream → 定时抽帧 → 模型结果回到 receive。

列表项显示的是设备名字，但它还在 Qt::UserRole 中保存了 QJsonObject。这个对象可以理解为一组带名字的值，例如 id 是设备编号，sourceType 是 local、rtsp 或 relay。显示名字不是唯一编号，真正的请求用 id。

```cpp
auto device = item->data(Qt::UserRole).toJsonObject();
openDevice(device);
```

第一行取出这一个列表项携带的数据，转成 JSON 对象；第二行把整组数据传给打开函数。这样不需要根据名字猜是哪台摄像头。JSON 在这里是数据格式，不是数据库，也不是另一个程序。

本机摄像头由 QMediaDevices::videoInputs 找到。localKey 用电脑标识与摄像头标识计算 SHA256，作为 sourceKey；刷新时后台用唯一键识别已登记设备，避免每次刷新都多一行。它不等于设备永久序列号，系统标识变化仍可能产生新登记。

```cpp
auto view = new LivePreview(tiles[channel]);
view->setCameraId(id);
embedLive(channel, view);
```

channel 是0到3的数组下标。tiles[channel] 是那格画面的容器。new 创建控件，view 保存它的地址；箭头表示调用这个对象的方法。把容器传作父对象，再加入布局，控件便显示在主界面里。父对象销毁时会管理子对象，替换画面时还会停止并延迟删除旧控件。

openGeneration 是每个通道的打开序号。网络请求返回时检查序号；如果期间已经换了设备，丢弃旧结果，避免慢请求把刚打开的新设备覆盖掉。

## 4 从视频帧到异常状态

本机使用 QCamera 和 QVideoSink 收帧；网络使用已有 DecodeTask 调用 FFmpeg 解码。帧进入容量为1的最新帧缓存，来不及处理的旧帧会被覆盖，不会无止境排队。实时检测是定期抽帧，默认间隔350毫秒，实际速度还受模型耗时影响。

LivePreview::sendFrame 只在模型就绪、没有正在处理的帧、且有新帧时发送。图像变为 JPEG，前面加4字节长度，经 QProcess 标准输入交给 detector/live_worker.py。Python 常驻加载 YOLO、Haar 人脸检测和 MediaPipe 手势模型，逐行输出 JSON，C++ 的 receive 解析并画框。

人脸检测只回答“这里有脸”，没有人脸录入、身份识别或人脸库。人员与手势也是模型推理结果，可能误判；本次公开手掌测试画面还被人员模型误检成 person，因此不能宣称准确率已评估。手势异常只是本项目暂定业务规则，不意味着现实中的危险行为。

```cpp
if (gestureAlarm) { ++positive; negative = 0; }
else { positive = 0; ++negative; }
```

positive 记录连续满足次数，negative 记录连续不满足次数。单次满足就加一，中间断一次就重新累计。只在“正常变异常”的边沿发起一次保存，而不是每帧保存。暂停时不累计结果，恢复后继续获取新画面；停止会关闭本控件自己的采集、解码与模型进程。

人员框阈值变化或手势告警勾选变化会重置计数。关闭告警后仍可看识别框，但不会按手势触发新异常。

## 5 异常怎样进入数据库

receive 检测到异常边沿 → 创建 pendingAlert → saveAlert → POST /api/events/gesture → 后端检查会话和设备权限 → 数据库事务 → 返回事件 id → 界面显示保存成功。

pendingAlert 包含 cameraId、eventKey、gesture、confidence、consecutive。cameraId 绑定实际设备，eventKey 是这一次告警的 UUID，重试时保留原值。UUID 可以理解为一串用于区别请求的编号，不是数据库密码。

```cpp
watcher->setFuture(QtConcurrent::run([body]() {
    Result r;
    r.data = ApiClient::request("/api/events/gesture", body, true, &r.error);
    return r;
}));
```

QtConcurrent::run 把网络请求交给工作线程，避免等待网络时卡住界面。[body] 是 Lambda 的捕获列表，表示复制一份 body 给这段函数使用；() 是参数列表，这里没有参数；花括号里是执行内容。这里只复制请求数据，没有让线程读取已经关闭的窗口。

Result 同时携带返回 JSON 和错误字符串。watcher 监听任务结束，finished 信号的槽回到界面对象所在的线程更新标签。失败时保留 pendingAlert 并显示重试；成功才清空并显示编号。窗口销毁后不会继续调用它的界面槽，但已经发出的后台请求仍可能完成。

后端确认用户已登录、设备启用、普通用户确实有该设备权限，再检查手势名称、置信度范围和连续次数。这里保存的是“授权客户端模型上报”的结果，后端没有再次拿原图推理，因此不能当成防篡改的服务端视觉证据。

## 6 库表与重复上报设计

cameras 增加 source_type：local 表示当前电脑采集，rtsp 表示直连网络视频，relay 表示已有媒体中继。source_key 是稳定去重标识，设有唯一索引。本机用标识哈希，直连网络设备用地址哈希。哈希不是加密，原始 RTSP 来源仍保存在 stream_url。

events 沿用既有事件表，新增数据的 event_type 为 gesture_open_palm，包含设备编号、UTC 时间、置信度、模型版本、文字描述和状态。实时手势没有自动生成录像，recording_id 为空，不能凭这条事件直接宣称已有录像证据。人脸图像和实时帧未保存到数据库。

live_event_receipts 是本次新增的请求回执表：request_key 主键保存请求 UUID，event_id 指向已保存事件，camera_id 指向设备，actor_id 记录上报用户。外键保证它们指向存在的数据。

相同 eventKey 重试，后台查回已有 event_id。不同 eventKey 但同设备10秒内再次上报相同手势，会合并到已有事件，并给新请求也写回执。即便等10秒后再重试这个请求，也仍然得到原事件，不会因冷却结束而重复新增。

事务可以理解为“一起完成的一组操作”。本次把 events、audit_logs、live_event_receipts 放在一个事务里，任何一步失败就回滚。SELECT cameras … FOR UPDATE 按设备锁住这一行，让并发请求依次判断10秒规则，避免同时查询都认为还没有事件。

当前每次报警只保留一条待重试请求，不是永久离线队列；数据库回执也尚无自动过期清理策略。真实长期部署需要进一步做保存容量、回执保留周期和失败补偿设计。

## 7 网络摄像头和 SDK 调研

RTSP 是取视频的协议；ONVIF 常用于发现设备、获取配置和视频地址；SDK 是厂商提供的开发工具包，可能还包含私有登录、云连接、回调取流。它们不是一个东西。拿到 SDK 也要核对设备型号、系统位数、接口文件、依赖、许可及登录方式。

海康支持相应 RTSP 接口的设备，可在表单填 IP、端口、摄像头账号密码、通道和主子码流。程序拼接 /Streaming/Channels/101 一类路径。其他厂商要填写已经确认有效的自定义 RTSP 地址，不能套用海康路径。登记进库不等于已连接，必须实际收到画面。

截图设备显示 Seetong TD53F18。App 分享链接是云分享入口，不是可直接交给 FFmpeg 的 RTSP 地址。对用户指定 IP 的80和554端口检查当时未连通；可能与设备在线情况、网络隔离或配置有关，不能据此断言永远不支持 RTSP。没有扫描其他设备或试猜密码。

厂商 FAQ 将 TD53F18 列为需要特定临时固件才能支持 ONVIF 的旧型号，并说明会损失 AP 等部分功能。本次没有刷固件。没有 ONVIF 也不能直接推断没有 RTSP。

GitHub 核对结果：elvalad/Seetong 是安卓监控客户端，含 Android 的 NetSDK.jar 和 .so，并非可直接载入 Windows x64 的 DLL；newstatic/SeetongDVR 用于读取存储卡 TPS 录像，不是实时云取流 SDK；silvije2/topsee_seetong_onvif_python_motion_detect 订阅 ONVIF 事件，前提是设备已经支持 ONVIF。

截至本次调研，没有找到已确认适配此设备、可合法直接集成的 Windows x64 SDK 包。没有把未知二进制放进工程。下一项设备接入材料应向卖家或天视通确认，可直接询问：“TD53F18 当前固件是否提供 RTSP 地址或 ONVIF？如需 SDK，请提供 Windows x64 包、头文件、库、示例、授权说明，并说明是否支持本型号的局域网取流和云设备取流。”

## 8 后台为什么独立启动

客户端负责界面、当前电脑摄像头和实时模型调用；C++ API 服务负责账号、权限和数据库；MediaMTX 负责已有中继；Redis 负责状态与限流；Python 检测服务负责原有录像检测。它们是多个进程。Qt Creator 运行一个 pro 对应的程序，不会自动启动其余全部进程。

backend_console.py 是本机开发启动与日志窗口，不是又写了一个后端业务服务。它调用 demo_launcher.py 确认服务就绪，读取 stack_status.py 的状态和 services.log，显示进程是否活着和脱敏日志。进程活着不等于每台摄像头都出图；端口健康也不能替代视频帧测试。

local_demo.py 记录各服务 PID、创建时间及可执行路径，停止时只处理自己记录且身份匹配的进程。PID 可能被系统复用，所以不能只看一个数字就结束进程。补充的退出诊断记录哪个管理服务退出及退出码，不输出摄像头密码或签名地址。

直连 RTSP 地址可能带摄像头凭据，后台只把它返回给有权限的请求者，普通设备列表不返回原始地址。当前直连方案会让获授权客户端接触原始来源，数据库也保存了来源凭据；尚未实现集中密钥管理。当前服务面向本机开发，不应把明文 HTTP 端口直接公开。

网络设备的“录制6秒”由后端读取网络地址录制；本机 USB 画面只存在当前客户端，不能让独立服务假装已经拿到它，所以该按钮明确拒绝本机录像。本次完成的是本机实时检测与事件元数据入库。

## 9 验证结果与边界

Qt6 MinGW64 Release 和 Debug 重新编译。接口测试覆盖设备去重登记、真实事件插入、相同请求重试、10秒合并、冷却后重试仍去重，以及匿名与无权限用户拒绝。真实模型联调使用 MediaPipe 公开手掌图片制成循环视频，经独立 RTSP 流进入主界面；连续识别触发后查询事件接口确认该事件存在。

本机 USB 摄像头实际收到视频帧；验证了与网络流同时嵌入、四画面及暂停后继续。公开样本不是现场摄像头手势的准确率评估，短时测试不是全天稳定性测试。本机摄像头画面未截图或写入教学文档。

样本流第一次测试因长关键帧间隔导致未及时出图；测试夹具改为每秒关键帧并使用低延迟编码后通过，没有降低业务手势阈值。正式网络摄像头仍需根据码流、网络和关键帧设置验证启动速度。

测试专用设备和对应事件、回执、审计记录在 finally 中按本次设备编号精确清理；测试画面截图只作本次验证。管理员自动登记的真实 USB 设备保留。旧库、原有账号、有效录像和其他任务文件不清理。

未验证或未实现：TD53F18 实机与 Windows SDK、真实海康硬件、人脸身份录入识别、自动本机录像、永久离线重试、多机长期压力与公开网络部署。上述项目不能在答辩中说成已完成。

## 10 面试问题与继续追问

问题1：为什么摄像头不再弹出独立窗口？答：把 LivePreview 从对话框改为普通 QWidget，以通道容器作父对象并加入已有布局，统一单画面和四画面管理。追问：只隐藏旧窗口够吗？追答：不够，旧摄像头和模型仍可能运行；替换时先停止，再延迟删除控件。

问题2：为什么双击设备要用编号？答：名称可重复或修改，数据库编号才是请求所需的设备身份。列表项同时保存 JSON 数据。追问：JSON 是数据库吗？追答：不是，它只描述一组名称和值；持久化仍由 MySQL 的表完成。

问题3：怎么避免每帧都插入异常？答：先累计3次有效张手识别，只在正常到异常的边沿发起请求；后台再按设备做10秒合并。追问：断网重试是否重复？追答：重用 eventKey，查询回执得到同一个事件编号，合并的请求也各自保存回执。

问题4：有唯一键为什么还加事务和行锁？答：唯一键解决相同请求重复，行锁让同设备的不同请求串行检查合并规则；事务保证事件、审计、回执一起成功。追问：锁会不会降低并发？追答：同一设备短暂串行，不同设备锁不同记录；实际吞吐仍需压测。

问题5：为什么不能在槽函数里直接等 HTTP？答：GUI 线程等待网络会卡住输入和刷新；QtConcurrent 在工作线程请求，watcher 完成后更新界面。追问：关窗口就取消请求吗？追答：不一定，界面回调解除不等于后台工作立刻停止，服务端仍可能保存成功，所以需要幂等。

问题6：你的人脸识别怎么设计？答：当前只做 Haar 人脸检测，没有身份比对、人脸录入和人脸库，不能称为身份识别。追问：人员识别有误报吗？追答：有，本次手掌样本出现 person 误框；目前验证链路，没有完整准确率评估。

问题7：SDK 找到就能接吗？答：还要匹配设备型号、Windows64、头文件和依赖、授权和认证方式，并实际收帧。追问：安卓 so 能直接给 Qt Windows 用吗？追答：不行，二进制平台和调用接口不兼容，得有对应 Windows 实现或另设安卓中转方案。

问题8：这是后端直接检测的事件吗？答：本次实时事件由授权客户端模型上报，后端检查权限与字段后保存；原有录像检测另走 Python 服务。追问：有录像证据吗？追答：本次实时手势没有自动录像，不能伪称有证据文件，也没有服务端二次视觉验证。

## 11 自己动手练一次
