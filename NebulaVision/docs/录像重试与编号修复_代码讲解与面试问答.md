# 录像重试与编号修复代码讲解

NebulaVision 学习记录　2026年11月3日

本次修复用户实际遇到的三件事：录像反复重试仍失败，选择无录像事件后还显示旧视频，列表事件编号很大且不连续。录像文件不丢弃；重试改用当前登录会话，保留可恢复信息；回放选择会清空上一段来源；列表序号与数据库ID分开显示。

本篇承接《异常录像与独立回放》。那篇关于“重开窗口后不能恢复待上传信息”的旧限制，由本次持久化信息补齐；尚未完成封片的内存帧仍不能在强制退出后恢复。用户现场视频没有上传到 GitHub 或放进本篇文档。

## 1 这次为什么会一直保存失败

原代码在报警时记住登录令牌，首次上传使用它。服务重启、退出登录或会话到期后，令牌可能失效；原来的 retry 仍然重复使用同一旧令牌，因此重复点击也可能持续失败。

现场排查发现，待上传文件已经存在，8秒视频能正常解码；用重新登录的会话提交同一文件后，原事件成功关联了录像。这证明该文件可用，不能简单归因于摄像头没有录下来。随后隔离测试专门复现旧会话失败，并验证修复后的同账号重试成功。

```cpp
token = ApiSession::token();
if (token.isEmpty()) {
    // 提示先登录原账号，保留录像文件。
    return;
}
upload();
```

ApiSession::token 取当前客户端的会话。这里不是修改密码，而是在用户重新登录后，使用新签发的会话去请求。服务端仍检查原事件上报者，不能因为换了令牌就允许其他账号上传或覆盖视频。

账号有权限与令牌还有效是两回事。相同用户重新登录可以获得新令牌；另一个用户即使登录成功，也不因此成为原事件的上报者。

## 2 重开程序后怎样继续重试

service/alertcliprecorder.h 增加 restore、cameraId 和 expectedFrames。对应 .cpp 在封片前用 QSaveFile 保存一份 pending.json，包含事件请求编号、摄像头编号、前段帧数和总帧数，不包含密码、令牌或视频内容。

已有 MP4 与这份小信息共同组成待上传任务。重新打开同一摄像头时，LivePreview::setCameraId 调用 restore，检查信息格式、设备编号和文件是否存在，再提示用户用原账号重试。

```text
alert-cache
  请求编号.mp4
  请求编号.mp4.pending.json
```

MP4 是视频，小 JSON 是“这段视频属于哪次报警”的说明。expectedFrames 单独保存，避免重开后内存帧列表为空，就错误地把总帧数传成0。上传成功并收到有效录像编号后，才删除本地待上传副本和它的信息文件。

只恢复匹配当前摄像头、格式正确、总帧数在允许范围内且视频存在的条目。不根据任意外部路径打开文件，文件名由事件UUID构造。每次恢复一个待处理条目，不表示已有无限离线队列或跨账号自动上传能力。

如果进程在原始帧还没编码成 MP4 时被强制结束，磁盘上没有完整视频，就不能凭 JSON 还原过去画面。早期版本没有信息文件的缓存也不能自动推断全部参数；本次现场旧文件按原回执核对后单独恢复，没有冒充所有旧文件都能自动恢复。

## 3 为什么选新事件却还看到旧视频

原 ReviewWidget::openRecording 检查到没有关联录像时直接返回，只改提示文字；上一段播放器来源和标题仍保留。因此用户选择新异常时，仍看见旧演示视频，容易误认为新报警录错内容。

现在增加 resetVideo：停止播放、取消旧下载结果、清空媒体来源、进度、时间和标题。选行时先清空旧视频；双击记录时再次检查。无录像就显示本条事件没有录像，不留下旧画面顶替。

```cpp
playback->stop();
playback->setSource(QUrl());
```

stop 是停止当前播放，setSource 空地址才清除原来的媒体来源。下载序号 downloadGeneration 同时变化，旧的异步下载即使晚到，也不能把旧视频重新放回来。

这里没有把无录像事件强行关联到某个已有视频。没有保存过的片段依然显示无录像，必须等待以后实际触发并成功保存的新短片。

## 4 列表为什么会出现44和45

数据库中的 AUTO_INCREMENT 主键是唯一身份，不是当前列表有多少条记录。测试曾插入并清理隔离数据，号码不会因删除自动退回；事务失败、删除等也可能留下空号。所以出现44、45，不代表仍存着45段录像。

本次不修改已存在的主键和关联。回放表格第一列改为“序号”，按当前查询结果连续显示；末列保留“事件ID”或“录像ID”。内部操作仍使用真实ID。

```cpp
序号 = (当前页 - 1) * 每页条数 + 当前行 + 1;
```

这是显示顺序，不会写回数据库。第一页显示1至10，第二页显示11至20；筛选、分页大小改变后重新计算。程序把真实ID保存在列表项的 Qt::UserRole+1 中，关联录像编号仍使用 Qt::UserRole。

ReviewWidget::openRecording、detectSelected 和回放标题已同步改为读取保存的真实ID，避免把显示序号错当数据库ID。一个事件可以关联一段录像，两张表各自分配编号，二者不必相等。

## 5 视频到底保存在哪里

本机当前正式录像目录为 C:\Users\23974\Desktop\jk\x\recordings。具体目录由后端配置的 recording_root 决定。alert-cache 是客户端待上传区，playback-cache 是授权下载的回放缓存，三者职责不同。

events 表保存异常时间、摄像头、类型、状态和 recording_id；recordings 表保存摄像头、开始与结束时间、文件名 object_key、大小和 ready 等状态；实际 MP4 放在录像目录。回放先经过登录和权限检查，再由后端按索引读取对应文件。

例如事件表中的 recording_id 指向录像表的一行，这行的 object_key 对应磁盘上的 MP4。数据库不是没用上，而是在管理“哪一次报警对应哪一个文件”。备份时既需要业务库，也需要录像文件；只复制其中一份不算完整备份。

视频本体也能存进 MySQL 的 BLOB 字段。MySQL 官方说明 BLOB 用于可变长二进制数据，同时提醒实际传输还受内存和通信缓冲限制。它不是技术上做不到，而是另外一种存储选择。

实际监控项目 Frigate 的官方文档明确区分 SQLite 中的录像信息与磁盘目录中的录像片段。因此“数据库存索引、文件系统存视频”有实际项目参考，不等于没有进行数据持久化。本项目继续沿用该分工；这次重试失败不会仅因改成 BLOB 自动消失。

参考：MySQL 8.0 BLOB 说明 https://dev.mysql.com/doc/refman/8.0/en/blob.html 。Frigate 数据库说明 https://docs.frigate.video/configuration/advanced/system/ 。Frigate 录像目录说明 https://docs.frigate.video/frigate/installation/ 。

## 6 修改清单和调用链

service/alertcliprecorder.h 和 .cpp：新增可恢复信息、restore 和独立总帧数；retry 更新当前令牌；成功后清理待上传副本。view/livepreview.cpp：打开设备时恢复其任务，并让恢复提示显示“重试录像”按钮。

service/apiclient.cpp：对事件回执不存在、视频校验失败给出对应提示，不把所有错误都压成同一种“保存不了”。view/reviewwidget.h 和 .cpp：加入 resetVideo、选行清理、连续显示序号、真实ID存取，更新录像播放与检测入口。

tests/clip_recovery_check.cpp：复现旧会话上传失败，销毁并重建录制对象，验证换账号被拒绝、原账号新会话成功；再检查列表序号与无录像选择是否清空旧视频。.pro 提供 Windows 回归入口，.py 只准备并清理本次隔离数据。

tests/embedded_device_check.cpp 与 linux_acceptance_gui.cpp：查找事件改为读取真实ID。CMakeLists.txt 把恢复测试并入可选 Linux 验收目标；linux_acceptance.py 增加对应通过标记检查，不跳过真实模型与视频测试。

重试调用链：打开同一设备 → setCameraId → restore 读取待上传信息 → 原账号登录 → retry 取当前令牌 → upload 使用磁盘MP4与保存的帧数 → 后端检查归属与视频 → 关联原事件 → 清理本地待上传副本。

## 7 验证结果与边界

Windows 隔离回归已通过旧会话失败复现、重建对象恢复、其他账号拒绝、原账号新会话重试成功，以及连续序号、选择无录像与双击无录像均清空上一段媒体来源。客户端 Release 和 Debug 编译通过。现场已有可解码短片已补关联回原事件，没有拿旧演示片段替代。

Linux 全流程与本次回归的最终任务链接见同期《Linux云端运行验收与代码讲解》。用户私有视频不在云端证据或源码中，云端测试只用公开图与人工色块样本；色块用于验证上传恢复，不用于冒充模型异常识别。

仍未实现：未封片原始帧的强制退出恢复、多条任务自动逐一排队上传、录像保留周期和文件库对账。事件没有录像时仍会明确显示无录像，而非自动使用其他片段。

## 8 面试问题与继续追问

问题1：为什么重试不能一直复用原令牌？答：令牌可能已失效，重复发送只会重复被拒绝；重试需要当前登录会话。追问：能换别人账号提交吗？追答：不能，后端继续核对原上报者和设备权限，本次测试专门验证其他账号被拒绝。

问题2：恢复录像为什么要保存一份小JSON？答：MP4 只保存视频，不包含业务事件UUID和原采样参数。追问：信息里需要存密码吗？追答：不需要，也没有保存令牌；恢复后仍需用户登录，再经过服务端授权。

问题3：停止播放就能防止旧画面误导吗？答：还需要清空媒体来源和标题，并取消旧下载结果。追问：如何取消已经发出的下载？追答：本次用序号使旧结果失效，不等于底层请求立刻停止；文件仍可能下载完成，但不会再次覆盖新选择。

问题4：主键有空号是不是数据库坏了？答：不是，主键保证身份唯一，不保证连续。追问：为了好看能重排主键吗？追答：不能随意重排，否则事件、录像、审计和其他外键可能关联错误；另设显示序号即可。

问题5：视频为什么没直接放MySQL？答：本项目把业务索引与大文件分开，数据库管理查询和权限，文件目录保存MP4。追问：BLOB能存吗？追答：能，但要考虑大文件传输、数据库体积、备份和访问方式，不能说关系数据库根本不支持视频。

问题6：重试成功能保证不重复建录像吗？答：后端锁定原事件，已有录像就复用编号，不覆盖先保存的片段。追问：本地文件什么时候删？追答：只有收到有效的成功编号才清理待上传副本，失败时保留，正式录像不作为测试垃圾删除。

## 9 练习

在回放列表区分“序号”“事件ID”和“录像ID”，解释为什么序号1可以对应事件ID45。选择一个无录像事件，确认画面、进度和旧标题都被清空。若看到待上传提示，用原账号登录后点重试；不需要改密码、删除数据库或重排主键。
