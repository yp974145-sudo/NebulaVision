## 按执行顺序理解
1. 主窗口进入回看页，调用refresh()。
2. refresh调用loadPage()。它查看下拉框，新事件模式调用loadEvents()。
3. loadEvents先清空表格，准备6列表头，再调用eventService.queryLatest()。
4. EventService找到本地JSON路径，交给EventRepository::queryLatest()。
5. 仓储创建DevDbConnection，读取配置并连接新库；失败就返回error。
6. QSqlQuery使用这条新连接执行SELECT。
7. while(query.next())逐行取值，放进EventData，再加入result.events。
8. 查询对象先销毁、连接管理对象后销毁，连接被释放。
9. 界面收到EventResult，有error就显示失败；没有error则逐行填表。0条数据显示暂无事件。

## DTO是什么
DTO是“用来传数据的对象”，这里就是EventData结构体。
```cpp
EventData event;
event.cameraName = query.value(1).toString();
result.events.append(event);
```
第一句创建一份事件数据；第二句读取第二列摄像头名称；第三句加入列表。
DTO本身不执行SQL、不创建控件，只带数据跨层传递。
EventResult同时带事件列表和错误信息，使“成功但0条”和“查询失败”可以区分。

## SQL怎么读
```sql
SELECT e.id, c.name, e.occurred_at, e.event_type,
       e.description, e.status
FROM events e
LEFT JOIN cameras c ON c.id=e.camera_id
ORDER BY e.occurred_at DESC, e.id DESC
LIMIT 100;
```
e、c是表的简写。FROM指定查询事件；LEFT JOIN按camera_id找摄像头名称，未匹配时仍保留事件。
ORDER BY按时间从新到旧，同一时间再按编号从大到小，保证次序确定。
LIMIT 100限制返回数量，不能将这100条数量当成全库总数。
时间按项目UTC存储约定直接显示，不进行本地时区换算。

## 界面怎么填表
```cpp
for (int row = 0; row < result.events.size(); row++) {
    EventData event = result.events.at(row);
    table->insertRow(row);
    table->setItem(row, 0, new QTableWidgetItem(event.id));
}
```
for逐条访问事件；at(row)取出事件；insertRow增加表格行；setItem将编号放进第0列。
其他5列同理。new创建单元格，交给表格后由表格管理其生命周期。
刷新先清空，避免失败时继续显示旧数据，让用户误以为查询成功。
新事件的最后一列是状态，因此双击不能继续沿用旧代码把最后一列当视频路径。

## 为什么分层
界面：显示和交互。
Service：安排业务请求、后续增加参数校验。本阶段比较薄，不强行堆逻辑。
Repository：执行SQL并转换结果。
连接管理：配置、连接校验和释放。
这样以后客户端改走HTTP接口，界面改动可以集中在数据获取边界；并非现在就已实现网络服务。

## 面试问答（先理解，不用背术语）
1. 为什么不在窗口里写SQL？界面只关心展示，数据库查询集中在仓储，修改表结构时不必散改窗口。
2. DTO是什么？只传数据的结构体，本次是EventData，没有数据库和界面操作。
3. 为什么时间相同再按id排序？给相同时间的记录确定顺序，为下一阶段分页准备。
4. 0条和失败怎样区分？error为空且列表为空表示成功但无数据；error非空表示失败。
5. 查询用信号槽后自动异步吗？不会，本次仍在界面线程同步调用，异步化安排在阶段4。
