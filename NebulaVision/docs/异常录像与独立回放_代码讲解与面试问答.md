# 异常录像与独立回放代码讲解

NebulaVision 学习记录　2026年11月3日

本次修复两个实际问题：手势异常原来只有数据库事件，没有自动录像；回放原来把文件送到监控通道，没有进度条和倍速。新版在手势报警时自动保存一段短片，成功后关联到事件，并在回放页直接播放。

本篇承接《设备嵌入与手势入库》。旧文档记录当时版本，“实时手势无自动录像”的旧限制已由本次改造补齐。人脸身份识别、远程 Seetong 云接入仍未实现；不能把本次录像能力理解为所有检测类型都自动录制。

## 1 怎样测试新版

双击资源目录中的“启动完整演示.cmd”，使用管理员登录，刷新设备，双击本机摄像头。在实时检测开启时，清楚地张开手掌，达到0.60且连续3次识别才会触发异常。

先看到“事件已入库”，接着等待约5秒采集以及封片上传，直到显示“异常录像已保存 #编号”。这两个状态分开：事件保存成功时，录像可能还在采集或上传，不能马上当成录像已完成。

点“回放”，默认打开“异常事件与录像”，点“全部记录”刷新。查看“异常录像”列，双击标有“可回放”的事件，画面直接在本页显示，不再跳到监控页。播放器上方显示事件编号和关联录像编号，方便确认对应关系。

底部支持播放与暂停、停止回放、拖动进度条，以及0.5、1、1.5和2倍速。“全部录像”还包含手动录制的普通视频；旧事件若没有保存过视频，就显示“无录像”，无法补出过去的画面。

手势持续不放不会每帧保存。连续3次不满足后解除异常，下一次重新满足才可能触发新事件。后端原有10秒合并规则继续生效，合并事件只保留先成功关联的那段录像。

## 2 这次改了哪些文件

新增 service/alertcliprecorder.h：声明短片录制对象，列出 sample、begin、finish、retry 等入口，以及历史帧、当前录像、待上传路径和状态。新增同名 .cpp：实现采样缓存、报警后的继续采集、MP4 编码和上传。头文件是“能做什么”，实现文件是“具体怎么做”。

view/livepreview.h 和 .cpp：实时控件持有 AlertClipRecorder；增加200毫秒采样定时器、录像状态和重试按钮；手势从正常变异常时，使用同一个 eventKey 启动事件保存和录像；暂停与停止会结束当前短片并清空历史缓存。

backend/apiserver.cpp：新增 POST /api/events/clip，检查用户和事件归属，校验上传视频，创建录像记录并关联事件。设置请求大小和最多两个并发封片任务，限制损坏视频的解码等待时间。复用原有库表，无需新增数据库表或重复建库。

service/apiclient.h 和 .cpp：请求接口增加可选令牌参数，短片使用触发时捕获的登录令牌，避免上传过程中换账号就变成新账号上报；录像上传的等待时间单独延长到25秒。

view/reviewwidget.h 和 .cpp：在回放页增加 QMediaPlayer、QVideoSink 与 QLabel、进度条、时间显示、倍速和标题；加入下载序号，防止慢的旧请求覆盖新选择；退出登录清除播放器来源和列表。view/mainwidget.cpp：删除“下载完切到监控页”的旧连接，退出登录时清空回放。

service/reviewquerytask.cpp：事件列表增加“异常录像”列，明确区分可回放与无录像。class15.pro：把新录制类的源文件和头文件加入 Qt6 构建。

tests/embedded_device_check.cpp：扩展真实模型联调，验证短片与事件关联、本页视频帧、拖动及2倍速。tests/embedded_pipeline_check.py：准备公开样本流，并按本次设备编号清理测试录像和文件。新增 tests/alert_clip_check.py：验证权限、坏视频拒绝、重试去重和授权下载。

## 3 为什么要保存报警前几秒

如果报警发生后才开始采集，动作开始的一瞬间可能已经过去。sample 每200毫秒保存一个缩小后的画面，最多保留15帧；以每秒5帧计算，就是最近最多3秒。第16帧到来时删除最旧一帧，缓存不会随运行时间增长。

```cpp
history.append(image);
if (history.size() > 15) history.removeFirst();
```

history 是一串 QImage。append 是追加，removeFirst 是删最前面的旧画面。这个设计常叫环形或滑动缓存，本实现使用有上限的列表，不是持续写硬盘。所有画面统一到640×360，保持比例并加黑边，不把4:3画面强行拉伸。

begin(eventKey) 在异常触发时，把已有历史帧放进当前录像 frames，再收集25个采样帧，也就是约5秒。总数最多40帧、约8秒。刚打开摄像头就报警时，历史不足3秒是正常的；测试中生成的一段约7.6秒，就是历史尚未攒满。

视频是5帧每秒的无声短片，保存原始画面，不叠加检测框；网络实时采样可能重复最近一帧。它适合当前演示和事件回看，不是高帧率全天录像。时间来自采样节奏与服务器事件时间，尚未做摄像头时钟精确同步。

## 4 从帧到 MP4 怎样走

主流程：LivePreview::receive 判断手势边沿 → 生成 eventKey → saveAlert 保存事件，同时 AlertClipRecorder::begin 保留前段画面 → sample 收满后调用 finish → upload 在工作线程封片 → 调用录像接口 → 显示保存结果。

```cpp
pendingAlert = { /* cameraId 与 eventKey 等数据 */ };
clipRecorder->begin(pendingAlert.value("eventKey").toString());
saveAlert();
```

eventKey 把两个动作串起来。事件先存，短片再用同一个编号找到它。它不是录像文件路径，也不是密码。采集只使用当前设备的 latest 画面，来源可以是本机 QCamera，也可以是已有网络解码器。

finish 不在 GUI 线程里等待整个编码过程。它复制帧、路径和触发时的令牌，交给 QtConcurrent 工作任务。FFmpeg 从标准输入读取 RGB24 帧，按5帧每秒编码为 H.264 MP4，并将索引移到文件头以便开始播放。

QImage 使用共享数据；追加和复制不一定立刻把每个像素再复制一遍。画面的生命期仍由对象管理，工作任务保留自己需要的数据，不能只拿指向界面临时变量的裸地址。

每个通道一次只处理一段待保存短片；历史缓存约10MB，最多40帧约28MB，编码和上传还会有额外开销。不能把单通道估算当成四通道实际峰值，长期资源压力尚未完整评估。

## 5 上传失败怎么办

临时封片保存在运行资源的 alert-cache 中，这是运行所需的待上传缓存，不是一份教学截图。上传成功后删除本地这份缓存，正式文件保存在服务端配置的 recording_root 中；数据库 recordings 只保存文件索引和元数据，不把整段视频塞进表里。

编码失败会删除本次不完整文件，并保留内存帧供当前窗口重试。上传失败则保留已编码文件，点击“重试录像”重传。只有服务端返回大于0的有效录像编号才显示成功，避免把数据库空值转换出的“0”当成已保存。

当前重试上下文保存在窗口内存里。重启后虽然失败文件可能仍在 alert-cache，却没有自动扫描恢复队列；关闭窗口、退出账号、强制结束进程都可能中断未完成的采集。保持客户端运行直到出现保存成功。暂停或停止会提前结束当前片段，不足1秒则不保存，后段可能少于5秒。

未保存成功的一段会占住该通道的待保存位置，提醒先重试，避免悄悄覆盖失败录像。因此它是有限缓存与人工重试方案，不是永久可靠的离线录像系统。

## 6 后端怎样确认事件和录像对应

POST /api/events/clip 接收 eventKey、preFrames、frames 和视频的 Base64 字符串。Base64 是把二进制变成可放进 JSON 的文本，会增加约三分之一体积；当前短片不超过12MB，请求体限制17MB，不用于上传小时级录像。

先检查会话、账号状态、手势事件回执和上报用户。普通用户还必须保持设备访问权限。只有原上报者可以给这条回执上传录像；不能随便拿一个别人的事件编号替换视频。

后端把视频写到自己生成的 UUID 文件名，客户端不能指定存储路径。FFmpeg 限时解码并重新编码，检查实际输出帧数；坏数据返回422。最多两个此类封片任务同时运行，忙时返回429，客户端保留待重试录像。

文件验证完成后开启数据库事务，锁住事件行，检查 recording_id。已有大于0的编号就复用原录像并删除本次多余文件，不覆盖先保存的视频。否则插入 ready 录像、更新 events.recording_id、写入审计，全部成功才提交。

```sql
SELECT recording_id FROM events WHERE id=? FOR UPDATE;
UPDATE events SET recording_id=? WHERE id=?;
```

第一句在同一事务中锁住这条事件，防止两个上传同时认为“还没有录像”。第二句把录像编号写回事件。它们之间还会创建 recordings 记录；不能单独只执行上面两句就认为完整保存了视频。

文件系统与 MySQL 不是同一个事务：普通失败路径会回滚索引并清理本次文件，但突然断电仍可能留下孤立文件，需要后续对账机制。后端验证视频能解码，不会再次验证视频里的手势；它仍是授权客户端上报的证据，不能声称具备防伪能力。

## 7 回放为什么换一个播放器

实时监控的目标是尽快显示最新帧，可以丢弃积压；历史回放要知道总时长、当前位置，并支持跳转和速度控制。原先 DecodeTask 向前读帧的接口没有这些能力，所以本次在 ReviewWidget 中使用 Qt 的 QMediaPlayer 播放授权下载的本地文件。

Qt6 通过 QVideoSink 接收实际视频帧，转成 QImage 后画到 QLabel，画面确实留在本页；Qt5 的兼容分支保留 QVideoWidget，但本阶段未重测 Qt5。

调用链：双击事件 → openRecording 从 Qt::UserRole 取关联录像编号 → 授权下载 → 检查下载序号和登录状态 → setSource 指定本地文件 → play。MainWidget 不再收到文件就切到监控页，因此监控通道内容保留。

```cpp
connect(speed, /* 选项变化信号 */, this, [this]() {
    playback->setPlaybackRate(speed->currentData().toDouble());
});
```

这是一段 Lambda。这里的 [this] 让代码使用当前回放窗口里的 playback 和 speed；空括号表示没有额外参数。每个倍速选项携带一个数字，取出来转成 double，交给播放器。定义连接时不会马上执行，用户改变选项后才执行。

durationChanged 更新进度条范围；positionChanged 更新当前时间和滑块；用户拖动时调用 setPosition。updatingSeek 区分“播放器自己更新滑块”和“用户要求跳转”，防止程序更新滑块又反过来反复跳转。

downloadGeneration 是下载序号，新的选择使旧序号失效。即便旧下载最后才完成，也不能覆盖刚选择的新录像。退出登录会清除媒体来源、列表和旧请求状态，不能继续显示上一账号的回放。

## 8 测试结果与未测边界

真实模型联调：使用 MediaPipe 公开手掌图片制成独立 RTSP 样本流，经主界面检测触发异常。生成的 MP4 约7.6秒、640×360、5帧每秒；事件关联录像后，Qt 回放页实际收到视频帧，进度条跳转、暂停后继续和2倍速通过。公开静态图循环是链路测试，不是现场动作准确率评估。

本机 USB 摄像头实际出帧，嵌入、四画面、暂停继续的检查通过；本机与网络源复用相同短片采样器。没有拍摄或保留用户现场做手势的录像来冒充测试结果。未测试远程 Seetong、长时压力、断电恢复、现场声音录制或全部操作系统。

接口检查通过：匿名拒绝、非上报者拒绝、错误帧数拒绝、假视频拒绝、有效视频入库、重复上传复用编号、事件关联、授权下载及无权限下载拒绝。客户端 Release 与 Debug 编译检查单独进行。

测试专用设备、事件、录像、回执、审计和正式存储中的本次测试文件，按本次设备编号精确清理；测试缓存和截图放在任务临时目录并在完成后删除。旧库、用户已有录像、模型和其他任务资源保留。

## 9 面试问题与继续追问

问题1：怎样保存报警前的视频？答：用容量固定的历史帧列表，每200毫秒采样，最多15帧。报警时复制历史，再追加后续25帧。追问：开机就报警能保证3秒前录吗？追答：不能，缓存尚未攒满，只保存实际已有部分。

问题2：事件入库和录像保存为什么分开显示？答：事件写入快，视频还需要采集、编码和上传。追问：事件成功、录像失败怎么办？追答：事件保留为无录像，界面显示失败并允许重试，不把它当成有视频。

问题3：重复上传会覆盖录像吗？答：锁住事件行，已有有效 recording_id 就返回原编号；每个事件只接收先成功的一段。追问：10秒内合并报警怎么办？追答：不同回执可指向同一事件，最终仍只关联一段，不能说每次动作都有独立短片。

问题4：为什么不用实时播放器直接回放？答：实时播放器偏向最新帧，现有接口没有时长和跳转；回放改用 QMediaPlayer 提供进度和倍速。追问：这还是手写 FFmpeg 解码吗？追答：监控保留原解码路径，回放使用 Qt Multimedia 的媒体后端，不能说回放时间轴是自己实现的底层解码。

问题5：为什么编码放到线程？答：同步等待 FFmpeg 完成会让 GUI 卡住，所以只在主线程收集帧，把封片和上传放到工作任务。追问：[this] 到处用安全吗？追答：界面槽可使用对象上下文自动断开，但独立长任务应复制数据，不能引用已销毁的窗口；本次编码任务复制帧和令牌。

问题6：数据库事务能保证视频和索引绝不失配吗？答：不能，文件系统不参加 MySQL 事务。正常失败会清理，突然断电仍需对账。追问：当前有完善对账吗？追答：没有，本次完成受控短片保存闭环，不能夸大成生产级存储系统。

问题7：上传成功就是可信异常证据吗？答：后端检查权限与视频可读性，关联的是客户端模型上报事件；没有服务端二次视觉推理或签名取证。追问：人脸是否录入了身份库？追答：没有，只有画面中的脸检测，本次保存的是异常短片。

## 10 练习

先正常监控几秒，再张开手掌触发，等待录像保存。记下事件编号和录像编号，在回放页找到同一事件，试着拖到中间并切到0.5倍速。然后打开 alertcliprecorder.cpp，找到15和25，解释它们为什么分别对应3秒和5秒。

不要为练习删除真实事件或修改数据库密码。文档不含本地账号文件、数据库口令和摄像头分享参数，可单独分享。公开测试样本来源为 https://storage.googleapis.com/mediapipe-assets/right_hands.jpg 。
